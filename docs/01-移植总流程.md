# 01 · 移植总流程

本文记录从「拿到一个 Windows 老游戏 + 一台没编译环境的掌机」到「能在 Ports 菜单里正常游玩」的完整路线，以及每一步判断「做对了没有」的依据。

---

## 一、起点与约束

| 事实 | 影响 |
|---|---|
| 游戏是 Windows 上跑的 jysdl-bh 引擎（SDL2 + Lua 5.2.4），脚本已被编成字节码 | 逻辑层改不动，只能在引擎侧和数据侧做文章 |
| 目标机是 TrimUI Brick：A133、1024×768、glibc 2.33、FAT32 卡 | 需要 aarch64 交叉编译、显示后端要适配、文件名大小写要精确 |
| 设备上没有编译器（gcc/make/python3/lua 全无，`/rom` 只读） | 唯一路径：PC 交叉编译后 scp 推送 |
| MainUI 常驻并占用 `/dev/fb0` 与 ALSA | 直写显示必须挂起 MainUI；音频要先确认可共享 |

---

## 二、决策树（先想清楚这四件事）

```
游戏引擎是 SDL2 还是 SDL1.2？
├─ SDL1.2 → 参考包（4in1）的 libSDL-1.2 可能"能抄"，但要先比对 DT_NEEDED 与后端字符串
└─ SDL2    → 别抄 S​DL1.2 的库（ABI 不同），看它是否有厂商 EGL，决定要不要自己直写 fb0

设备有 GPU/EGL 厂商后端吗？
├─ 有，且能出画面 → 先跑通默认路径，直写只是"可选优化/绕开合成器"
└─ 无 / 画面被 MainUI 盖掉 → 必须自己直写 /dev/fb0

游戏界面是按多少排版的？
└─ 打开 set.ini 看 CONFIG.Width/Height；再看有没有 1280×720 的全屏底图（本例 TITLE.png）
   内部渲染面 ≥ 排版宽度，否则左右裁边；面板不够就等比缩小，不要改画布

输入是键盘还是手柄？
└─ 引擎只读 SDL 键盘事件而掌机是手柄 → 必须加 gptokeyb 这类"手柄转键盘"的中间层
```

---

## 三、九步路线与验收标准

### 步骤 1：判定参考包能不能复用

- 工具：`tools/elf_needed.py`（解析 `DT_NEEDED`）、`strings` 扫后端名（`mali`/`dummy`/`fbdev`）。
- 结论判据：两边 SDL 大版本一致 **且** 库里有对方需要的视频后端，才谈得上"换库"。
- 本例结论：4in1 是 SDL1.2 + 引擎自己写 fb0；我们是 SDL2 + Mali/EGL。**换库无解**，改为复刻直写。

### 步骤 2：搭交叉编译链

- zig 0.13 内置 clang，target 固定 `aarch64-linux-gnu.2.33`（glibc 不得高于设备）。
- sysroot 直接用设备上的 `/usr/trimui/lib`（只有 `.so.0`，链接写全名 `-l:libSDL2-2.0.so.0.3000.8`）。
- 验收：编出来的 ELF `e_machine=0xB7`、解释器 `/lib/ld-linux-aarch64.so.1`，设备上 `ldd` 不存在时用 `readelf`/试跑判断。

### 步骤 3：让引擎出画面（直写 fb0）

- 加 `JY_FBDEV=1` 开关，默认仍走 EGL；直写只在 32bpp 时启用。
- 验收：`dd if=/dev/fb0 of=/tmp/x.raw bs=4096 count=768` 抓到完整 1024×768 画面，中文不乱码。

### 步骤 4：修排版与缩放

- 内部渲染面 = 排版宽度（本例 1280×720）；面板 1024×768 → 0.8 等比缩到 1024×576。
- 验收：载入进度列表 11 行两端完整、标题右侧书册出现、上下机框四边都在。

### 步骤 5：打通输入

- gptokeyb 先起（虚拟键盘），引擎后起（枚举到它）。
- 验收：`jyinject` 注入 → 引擎 `keylog.txt` 有 `sym=...` → 抓帧看到菜单高亮移动。三层都要有证据。

### 步骤 6：修音频

- 先排环境（`/dev/snd`、`amixer`、`aplay` 都正常）再动代码。
- 本例五处：解码入口、扩展名大小写、`CONFIG.MP3`、音量、默认开关。
- 验收：日志 `music play OK ... active=1`；真机耳朵听到。

### 步骤 7：修中文与编码

- 脚本是 GBK；引擎 `luaL_loadfile` 文本/字节码都吃；改脚本必须按 GBK 写回。
- 验收：进入游戏全流程零乱码，`error.txt` 为空。

### 步骤 8：修立绘尺寸

- 先补回 `LoadPicture` 的 zoom 参数，再定「只缩不放」，最后改固定框。
- 验收：大图不铺满屏、小图不拇指，两者最长边都到 146。

### 步骤 9：修资源路径与功能

- FAT32 精确大小写准备资源；菜单类功能「点了就退回」优先怀疑资源存在性判断。
- 验收：功能真机可用 + 抓帧留证。

## 四、时间线（真实顺序，含弯路）

| 阶段 | 做了什么 | 结果 |
|---|---|---|
| 1 | 解析 4in1 的 ELF / 库 / 启动脚本 | 判定不能补库 |
| 2 | 写出 fbdev 直写后端并编进引擎 | 首次真机出画面 |
| 3 | 发现 MainUI 抢屏 | 确定"必须由启动器挂起 MainUI" |
| 4 | 内部面误设 960×720 | 文字被切 → 回 1280×720 |
| 5 | 缩放 0.75 + 整圈机框 | 框完整但画面小 → 0.8 + 上下机框 |
| 6 | 最近邻太糊 | 改盒式平均，CPU 66%→79% |
| 7 | 按键无反应 | gptokeyb + jyinject 验证链路 |
| 8 | BGM 无声 | 五处修复，`active=1` |
| 9 | 立绘过大 | zoom → 只缩不放 → 固定框 146（中途把 NPC 小图压成拇指图，回退重做） |
| 10 | 文字放大尝试 | 字符超出边框，**已否决并回滚** |
| 11 | 内置攻略打不开 | 定位到 `data/Help` 大小写，修复并留证 |

## 五、每一步都要留证据

本项目坚持「先抓帧、再改」，证据类型固定三种：

1. **画面证据**：`/dev/fb0` 抓 raw → `raw2png.py` 转 PNG，改之前一帧、改之后一帧。
2. **日志证据**：引擎 `fbdev.txt` / `debug.txt` / `error.txt`，加一段诊断开关（`JY_*` 环境变量）再跑。
3. **链路证据**：`/proc/<pid>/fd` 看设备节点是否被打开、`pidof` 看进程是否并存。

只有三种证据都指向同一结论，才认为这一步做完了 —— 否则「命令跑完了」不等于「功能对了」。
